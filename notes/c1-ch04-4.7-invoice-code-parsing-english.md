## 1. What parsing is

Parsing means dividing a large text or code into smaller meaningful parts. In business data, each part of a code may carry separate information.

```python
invoice_no = "INV-2024-007"
parts = invoice_no.split("-")

print(parts)
print(f"Prefix: {parts[0]}")
print(f"Year: {parts[1]}")
print(f"Serial: {parts[2]}")
```

**Output**

```text
['INV', '2024', '007']
Prefix: INV
Year: 2024
Serial: 007
```

The three invoice parts have three business meanings. After parsing, report fields can be created from the raw code.

Important lines:

- `split("-")` divides the code at each hyphen.
- `parts[0]` is the prefix.
- `parts[1]` is the year.
- `parts[2]` is the serial.

## 2. Mapping a code format

Before parsing, map the code format. A format map records what each part or position means.

```python
invoice_no = "INV-2024-007"

print("Format: PREFIX-YEAR-SERIAL")
print("Prefix length:", len("INV"))
print("Year length:", len("2024"))
print("Serial length:", len("007"))
```

**Output**

```text
Format: PREFIX-YEAR-SERIAL
Prefix length: 3
Year length: 4
Serial length: 3
```

A format map makes the boundaries for `split()` or slicing precise. If a business-code format changes, do not blindly use the old boundaries.

## 3. Parsing a customer code

In customer code `"C-1023"`, `C` is the type marker and `1023` is the customer ID.

```python
customer_code = "C-1023"
parts = customer_code.split("-")

customer_type = parts[0]
customer_id = parts[1]

print(f"Type: {customer_type}")
print(f"Customer ID: {customer_id}")
```

**Output**

```text
Type: C
Customer ID: 1023
```

The list parts were given business-meaningful variable names. `customer_id` is still a string because it is a text part of a code. Convert it later only when a numeric operation is actually required.

The same extraction with indexing:

```python
customer_code = "C-1023"
print(customer_code[0])
print(customer_code[2:])
```

**Output**

```text
C
1023
```

`split()` is readable, while slicing can be compact for a fixed format.

## 4. Parsing a product code

A product code may contain multiple parts. In `"P-RICE-025"`, the parts are a type, product name and item number.

```python
product_code = "P-RICE-025"
parts = product_code.split("-")

print(f"Type: {parts[0]}")
print(f"Product: {parts[1]}")
print(f"Item number: {parts[2]}")
```

**Output**

```text
Type: P
Product: RICE
Item number: 025
```

Putting each part into a separate variable makes a report easier to read. The leading zero in the item number is preserved, so keeping it as text is safe.

## 5. Parsing an invoice code

The prefix, year and serial can be reported separately from invoice code `"INV-2024-007"`.

```python
invoice_no = "INV-2024-007"
prefix, year, serial = invoice_no.split("-")

print(prefix)
print(year)
print(serial)
```

**Output**

```text
INV
2024
007
```

Three variables receive the three list items. This is called unpacking. The important rule is that the variable order must match the part order.

Wrong order:

```python
prefix, serial, year = invoice_no.split("-")
print(year)
```

**Output**

```text
007
```

Python raises no error, but the business meaning is wrong. This is a silent logic bug.

## 6. `split()` and field names

After parsing, use clear field names. Keeping only `parts[0]` and `parts[1]` increases the chance of a later mistake.

```python
invoice_no = "INV-2024-007"
parts = invoice_no.split("-")

invoice_prefix = parts[0]
invoice_year = parts[1]
invoice_serial = parts[2]

print(f"Prefix: {invoice_prefix}")
print(f"Year: {invoice_year}")
print(f"Serial: {invoice_serial}")
```

**Output**

```text
Prefix: INV
Year: 2024
Serial: 007
```

Meaningful variable names make code easier to understand. `invoice_year` clearly communicates the field's purpose.

## 7. Taking fixed fields with slicing

Slicing can also extract fields from a fixed-format invoice when the hyphen positions are known.

```python
invoice_no = "INV-2024-007"

invoice_prefix = invoice_no[:3]
invoice_year = invoice_no[4:8]
invoice_serial = invoice_no[9:]

print(invoice_prefix)
print(invoice_year)
print(invoice_serial)
```

**Output**

```text
INV
2024
007
```

Slicing is compact, but it depends on a fixed format. If the separator position changes, the boundaries must change too. For general parsing, `split()` is usually more readable.

## 8. Code validation

Basic validation can happen before or after parsing. Checking the prefix, separator count and number of parts is useful.

```python
invoice_no = "INV-2024-007"
parts = invoice_no.split("-")

is_invoice = invoice_no.startswith("INV-")
has_two_separators = invoice_no.count("-") == 2
has_three_parts = len(parts) == 3

print(is_invoice)
print(has_two_separators)
print(has_three_parts)
```

**Output**

```text
True
True
True
```

All three checks pass. These are not complete validation, but they are useful first checks for a beginner parsing workflow.

Malformed code:

```python
bad_code = "INV-2024"
parts = bad_code.split("-")
print(len(parts))
```

**Output**

```text
2
```

Fewer than the expected three parts may mean that the code is incomplete. Therefore, checking the parts length matters.

## 9. Report-ready extraction

The boss wants report fields from a raw invoice list. We will parse two fixed records first so that field extraction stays clear.

```python
invoice_a = "INV-2024-007"
invoice_b = "INV-2025-003"

parts_a = invoice_a.split("-")
parts_b = invoice_b.split("-")

print(f"{parts_a[1]} | serial {parts_a[2]}")
print(f"{parts_b[1]} | serial {parts_b[2]}")
```

**Output**

```text
2024 | serial 007
2025 | serial 003
```

Year and serial are separated for a management report. The same parsing logic can later be used with a loop.

## 10. A complete parsing workflow

Clean raw input, then extract fields from customer, product and invoice codes.

```python
raw_customer = " c-1023 "
raw_product = " p/rice/025 "
raw_invoice = " inv/2024/007 "

customer_code = raw_customer.strip().upper()
product_code = raw_product.strip().upper().replace("/", "-")
invoice_code = raw_invoice.strip().upper().replace("/", "-")

customer_parts = customer_code.split("-")
product_parts = product_code.split("-")
invoice_parts = invoice_code.split("-")

print(f"Customer ID: {customer_parts[1]}")
print(f"Product: {product_parts[1]}")
print(f"Invoice year: {invoice_parts[1]}")
print(f"Invoice serial: {invoice_parts[2]}")
```

**Output**

```text
Customer ID: 1023
Product: RICE
Invoice year: 2024
Invoice serial: 007
```

The workflow is:

- keep the raw fields;
- apply field-specific cleaning;
- split the standardised codes;
- report the named parts.

## Troubleshooting

### Problem 1: The wrong field is printed

- **What happens:** The serial appears where the year should be, or another part is shown.
- **Likely cause:** The parts index or unpacking order is wrong.
- **Steps:** Print the complete parts list first, then write down the meaning of each index.
- **Prevention:** Use meaningful names such as `invoice_year`.

### Problem 2: `ValueError` appears during unpacking

- **What happens:** `prefix, year, serial = code.split("-")` raises an error.
- **Likely cause:** The code does not contain exactly three expected parts.
- **Steps:** First assign `parts = code.split("-")` and print `len(parts)`.
- **Prevention:** Check the expected part count before unpacking.

### Problem 3: The product code's leading zero disappears

- **What happens:** Item number `025` appears in a different form.
- **Likely cause:** The code part was treated as a number instead of text.
- **Steps:** Keep the parsing result as a string unless numeric calculation is needed.
- **Prevention:** Treat identifiers and measurable quantities as different concepts.

### Problem 4: A dirty code cannot be parsed

- **What happens:** Extra spaces or lowercase letters remain in the parts.
- **Likely cause:** Cleaning did not happen before splitting.
- **Steps:** Apply `strip()`, case conversion and known separator replacement, then split.
- **Prevention:** Follow the order raw -> clean -> parse.

## Common Misconceptions

1. **Wrong:** Parsing only means writing `split()`. -> **Correct:** Finding the business meaning of the parts is also parsing.
2. **Wrong:** `parts[1]` has the same meaning in every code. -> **Correct:** Meaning depends on the code format.
3. **Wrong:** Serial `007` must always become an integer. -> **Correct:** Keep it as a string when it is an identifier so the leading zero remains.
4. **Wrong:** A valid prefix makes the whole code valid. -> **Correct:** Separator count and part count also need checking.
5. **Wrong:** Overwriting the raw code causes no problem. -> **Correct:** The raw value is useful for audit and debugging.

## Key Idea

Parsing means breaking a code apart and finding its business meaning. Clean the input, use `split()` or slicing to separate fields, store them in meaningful variables, and check the prefix, separators and part count. Keep identifiers as strings when their leading zeros matter.

**Rhyme 1:** Break the code, know the meaning, keep each field right,
**Rhyme 2:** Clean then parse for a report precise and bright.
